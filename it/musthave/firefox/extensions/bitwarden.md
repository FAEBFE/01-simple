# Bitwarden: рекомендуемые настройки и best practices

Bitwarden удобно использовать не только как хранилище паролей, но и как центральное место для данных восстановления аккаунтов.

Главный принцип:

> **Каждый сервис получает уникальный пароль, а данные для восстановления хранятся вместе с соответствующей записью.**

## 1. Master password

Master password Bitwarden — исключение из общего правила.

Его не генерируем в Bitwarden и не используем больше нигде.

Создаём длинную уникальную парольную фразу, которую можем надёжно запомнить.

Например, не используем:

```text
один и тот же пароль для Bitwarden и Proton
```

Bitwarden отдельно подчёркивает, что master password невозможно восстановить или сбросить сотрудниками Bitwarden. Поэтому его потеря может привести к потере доступа к хранилищу.

## 2. Включаем двухэтапную аутентификацию

Открываем:

**Bitwarden Web Vault → Settings → Security → Two-step login**

Настраиваем как минимум один дополнительный фактор.

Предпочтительный вариант — **Authenticator app** или **FIDO2/WebAuthn**.

Bitwarden поддерживает несколько методов одновременно, включая FIDO2/WebAuthn, authenticator app и аппаратные ключи.

### После включения 2FA

Сразу сохраняем **recovery code**.

Bitwarden предупреждает: если потерять одновременно устройство/метод 2FA и recovery code, можно потерять доступ к vault.

Recovery code сохраняем в безопасном месте.

## 3. Пароли генерируем только Bitwarden

Для каждого нового аккаунта:

**Bitwarden → Generator → Password**

Создаём уникальный пароль и сразу сохраняем его в записи Login.

Не используем один пароль для:

```text
GitHub
Proton
Bitwarden
Google
Microsoft
```

Каждый сервис получает собственный пароль.

Bitwarden рекомендует использовать генератор и позволяет настраивать длину, набор символов и другие параметры. При этом Bitwarden отдельно предупреждает не вводить без необходимости чрезмерные ограничения на специальные символы и цифры: слишком жёсткие требования могут уменьшать пространство возможных паролей.

## 4. Одна запись — один аккаунт

Для обычного сервиса используем тип:

**Login**

Например:

```text
GitHub
├── Username: faebfe
├── Password: ********
├── URI: https://github.com
└── Notes:
    Recovery email: ...
    Дополнительная информация: ...
```

Для Proton:

```text
Proton Mail
├── Username: name@proton.me
├── Password: ********
├── URI: https://account.proton.me
└── Notes:
    Recovery email: ...
    Recovery information: ...
```

Так данные аккаунта и его восстановления находятся в одном месте.

## 5. Secure Notes используем для самостоятельных секретов

Если информация не относится непосредственно к логину, можно использовать:

**New → Secure Note**

Например:

- recovery information;
    
- резервные коды;
    
- лицензионные ключи;
    
- секретные настройки;
    
- другую конфиденциальную информацию.
    

Но не стоит превращать одну огромную Secure Note в свалку всех секретов.

Лучше придерживаться принципа:

**одна сущность → одна запись.**

## 6. Организуем vault папками

Bitwarden позволяет создавать **Folders** для организации личного vault.

Например:

```text
00-critical
01-email
02-development
03-services
04-social
05-shopping
06-other
```

Но папки не являются механизмом безопасности. Они только организуют отображение записей.

Поэтому не стоит создавать десятки уровней каталогов без необходимости.

## 7. Настраиваем автоматическую блокировку

Открываем:

**Bitwarden → Settings → Security → Vault timeout**

Не используем:

**Never**

Bitwarden прямо предупреждает, что при `Never` ключ шифрования остаётся на устройстве в незашифрованном виде, что снижает безопасность.

Практический вариант:

```text
Vault timeout: 15 minutes
Timeout action: Lock
```

Точное значение зависит от того, насколько часто используется Bitwarden и насколько физически защищено устройство.

## 8. Не путаем Lock и Log out

**Lock** оставляет зашифрованные данные vault на устройстве и позволяет разблокировать его локально.

**Log out** удаляет данные vault с устройства и при следующем входе требует полноценной аутентификации.

Bitwarden отдельно описывает это различие в документации.

Для обычной повседневной работы удобнее **Lock**.

## 9. Используем autofill

Для сайтов сохраняем правильный URI в записи Login.

Bitwarden использует URI, чтобы определить, когда предлагать автозаполнение.

Не стоит без необходимости добавлять в одну запись множество несвязанных доменов.

## 10. Периодически проверяем vault

Если доступна функция **Vault Health Reports**, периодически проверяем:

- слабые пароли;
    
- повторно используемые пароли;
    
- скомпрометированные пароли;
    
- незащищённые аккаунты;
    
- отсутствие 2FA.
    

Bitwarden описывает эти проверки как инструмент аудита состояния vault.

## 11. Что в итоге должно получиться

Для каждого важного аккаунта:

```text
Сервис
├── уникальный username
├── уникальный пароль
├── правильный URI
├── 2FA
├── recovery information
└── резервные коды
```

А для самого Bitwarden:

```text
Bitwarden
├── уникальный master password
├── 2FA
├── recovery code
├── разумный vault timeout
└── резервный план восстановления
```

### Главный принцип

**Bitwarden — единственное место, где мы не придумываем отдельные пароли вручную.**

Для всех обычных аккаунтов пароль генерирует Bitwarden.

**Master password Bitwarden — исключение:** его создаём как длинную уникальную парольную фразу, которую можем запомнить.

Таким образом, компрометация одного сервиса не должна автоматически давать доступ к остальным.
